# Правила роботи з Claude Code (універсальні, для будь-якого проєкту)

Мета: завжди розуміти, **що робиться, що зроблено, що перевірено** — і не зламати прод.

---

## 1. Три середовища — три зони відповідальності

| Середовище | Де | Хто змінює | Дані |
|---|---|---|---|
| **Локальне (dev)** | ваш ПК, `runserver` | Claude + ви | тестова/копія бази, `.env` з `DEBUG=1` |
| **Репозиторій (GitHub)** | `main` + гілки `task/*` | ви (push, merge) | без секретів і без бази |
| **Прод (сервер)** | Ubuntu, systemd | **тільки ви**, тільки через `deploy.sh` | робоча база, `.env` з `DEBUG=0` |

Головне правило: **Claude працює лише локально.** Він не має доступу до сервера (`ssh`/`scp` заборонені в `.claude/settings.json`) і не робить `git push`. Шлях коду на прод завжди проходить через вас: рев'ю → merge → бекап → деплой.

---

## 2. Життєвий цикл однієї задачі

```
 1. /clear                      ← чистий контекст для нової задачі
 2. /task-start ЗАДАЧА-N ...    ← режим Plan: дослідження + план, коду немає
 3. ви: правите/затверджуєте план
 4. гілка task/N-...            ← main не чіпаємо
 5. реалізація малими кроками   ← Manual або Accept edits; після кроку — тести
 6. /diff                       ← ви дивитесь, що змінилось
 7. /task-finish                ← тести, ruff, рев'ю субагентом, документи, коміт
 8. ви: merge у main, git push
 9. /predeploy                  ← чекліст: міграції, .env, відкат
10. ви: бекап бази → deploy.sh → перевірка сайту
```

Задача вважається **зробленою**, коли: тести зелені, ruff чистий, рев'ю без блокуючих проблем, документи оновлені, зміни в `main`. Задеплоєною — коли пройшов крок 10.

---

## 3. Як бачити, що відбувається

| Питання | Де дивитись |
|---|---|
| Що Claude робить **зараз**? | `Ctrl+T` — список задач у сесії; `Ctrl+O` — детальний журнал дій |
| Які **агенти** працюють? | панель під полем вводу, `/tasks` (Enter — журнал агента) |
| Що **змінено** в коді? | `/diff`, diff у вікні PyCharm, `git status` |
| Що **зроблено** в проєкті? | `docs/TASKS.md` (стан), `CHANGELOG.md` (для людей), `git log` |
| **Чому** зроблено саме так? | `docs/DECISIONS.md` |
| Як працює система? | `PROJECT.md` |
| Щось пішло не так? | `Esc` — зупинити; `Esc Esc` / `/rewind` — відкотити; `git checkout -- файл` / `git reset` — відкат через git |

## 4. Режими і рівень довіри

- **Нова задача / незнайомий код** → `Plan`, потім `Manual` (кожна дія з підтвердженням).
- **План затверджено, крок зрозумілий** → `Accept edits` (файли — без питань, команди — з питаннями), але `/diff` після кожного кроку.
- **Рутина з добрими тестами** → можна `Auto`.
- `bypassPermissions` — не використовувати.

Правила дозволів живуть у файлах, а не в пам'яті:
- `.claude/settings.json` — спільні для проєкту (комітиться);
- `.claude/settings.local.json` — ваші особисті (у `.gitignore`). Сюди Claude сам записує «так, і не питати більше».

## 5. Тестування

- **Кожна зміна логіки = тест.** Спершу тест, що відтворює баг/вимогу, потім код.
- **Жодних реальних API в тестах.** Відповіді провайдерів — у `fuel/tests/fixtures/` (знеособлені), мережа — через mock.
- Обов'язкові сценарії для інтеграцій: успіх, порожня відповідь, помилка, повторний запуск (ідемпотентність).
- Перед комітом: `python -m pytest -q`, `python -m ruff check .` і `python -m ruff format --check .` (проєкт відформатований повністю з ЗАДАЧІ-5).
- Ручні «пробні» скрипти до реальних API — окремо в `scripts/probes/`, вони не є тестами і не запускаються pytest.
- Для складної задачі доручайте тести окремому субагенту (`test-writer`), а рев'ю — іншому (`code-reviewer`): так код не перевіряє сам себе.

## 6. База даних і міграції (найризиковіше місце)

1. Кожну міграцію читаєте ви (`python manage.py sqlmigrate fuel 00NN`).
2. Деструктивні зміни (видалення полів, зміна типів) — у два релізи: спершу додати нове і перенести дані, потім видалити старе.
3. **Перед кожним деплоєм — бекап бази.** Без бекапу деплой не робиться.
4. Локально працюйте з копією продакшн-бази лише якщо вона знеособлена; інакше — з тестовими даними.
5. Для кожної міграції знаєте команду відкату: `python manage.py migrate fuel <попередня>`.

## 7. Секрети

- Секрети лише в `.env` (у `.gitignore`), шаблон — `.env_example` з порожніми значеннями.
- Claude заборонено читати `.env` (правило `deny` у налаштуваннях). Якщо треба знати, яка змінна потрібна, — дивиться в `.env_example`.
- Різні `.env` для dev і прод: різні `DJANGO_SECRET_KEY`, `DEBUG`, `ALLOWED_HOSTS`.
- Ключ потрапив у чат, скріншот чи коміт → вважайте скомпрометованим і перевипускайте.

---

## 8. Git

- `main` = те, що можна викласти на прод у будь-який момент.
- Одна задача — одна гілка `task/<N>-<опис>`; невеликі коміти з повідомленнями `ЗАДАЧА-N: що зроблено`.
- Перед злиттям: `git diff main...HEAD` прочитано вами.
- Тег на кожен деплой: `git tag v0.4.0 && git push --tags` — тоді відкат = `git checkout v0.3.0`.

## 9. Документація: що де лежить

| Файл | Для кого | Що містить | Коли оновлюється |
|---|---|---|---|
| `CLAUDE.md` | Claude | правила, команди, заборони | рідко, коли змінюються правила |
| `PROJECT.md` | люди + Claude | домен, архітектура, провайдери, модель даних | коли змінюється логіка |
| `docs/TASKS.md` | ви | що в роботі, що зроблено, що далі | на старті і завершенні задачі |
| `docs/DECISIONS.md` | майбутні ви | чому вибрали саме так | при неочевидних рішеннях |
| `docs/WORKFLOW.md` | ви | цей документ | рідко |
| `CHANGELOG.md` | користувачі, деплой | що змінилось, що врахувати при деплої | кожна задача + кожен реліз |
| `deploy/SERVER_SETUP.md` | ви | як підняти сервер з нуля | при зміні інфраструктури |

Правило: **документацію оновлює та сама задача, що змінила код** (це входить у `/task-finish`), інакше вона застаріває.

---

## 10. Контекст і сесії

- Нова задача → `/clear`. Довга сесія → `/compact`. Великий контекст погіршує якість.
- Давайте Claude точні посилання: `@fuel/services.py`, а не «там, де синхронізація».
- Для консультацій і обговорень без зміни коду — чат Claude (проєкт у застосунку) або `/btw`.
- Наприкінці дня: `/rename` сесії і короткий запис у `docs/TASKS.md` — завтра продовжите з `claude -c`.
